\label{ch:system_analysis}

\section{Overview}
The \textbf{VR Driving Simulator} project aims to provide a high-fidelity training and evaluation environment for driving schools. 
The simulator models real-world driving dynamics using virtual reality and custom-built physical input devices (steering wheel, pedals, and gear shifter). 
This chapter presents a comprehensive analysis of requirements, constraints, design alternatives, and system architecture that directly address the research gaps and problem statement identified in Chapters~\ref{ch:intro} and~\ref{ch:lit_review}.

\section{Requirements Analysis}

\subsection{Functional Requirements}
Based on the identified research gaps and driving school needs, the system must fulfill the following functional requirements:

\textbf{FR1: Realistic Vehicle Control Input}
\begin{itemize}
    \item Accept analog steering input with proportional angle mapping (0–900° rotation range)
    \item Process independent accelerator, brake, and clutch pedal inputs with pressure sensitivity
    \item Support gear selection for both automatic (P, R, N, D) and manual (1–6, Reverse) transmissions
    \item Maintain input latency $<$ 50ms to preserve motor skill feedback loop~\cite{Harari2021}
\end{itemize}

\textbf{FR2: Immersive Visual and Audio Rendering}
\begin{itemize}
    \item Deliver stereoscopic 3D rendering at minimum 72 FPS per eye to minimize motion sickness~\cite{Lindal2019,Weidner2017}
    \item Provide 90–110° field of view matching Meta Quest 3 specifications
    \item Implement spatial audio with direction-dependent engine sounds, traffic noise, and ambient effects~\cite{GilCarvajal2024}
    \item Render photorealistic vehicle interiors (dashboard, mirrors, gear shifter) for high-end car models (Mercedes-Benz, BMW, Audi)
\end{itemize}

\textbf{FR3: Accurate Vehicle Physics Simulation}
\begin{itemize}
    \item Model realistic acceleration, braking distances, and cornering dynamics based on vehicle mass, tire friction, and road conditions
    \item Simulate clutch engagement points, gear ratios, and engine stalling for manual transmission training
    \item Implement collision detection with appropriate force feedback and damage visualization
    \item Support dynamic weather conditions (rain, fog) affecting visibility and traction
\end{itemize}

\textbf{FR4: Performance Monitoring and Assessment}
\begin{itemize}
    \item Log driving metrics: speed profile, lane deviation, braking smoothness, gear shift timing, steering angle variance
    \item Generate automated assessment scores based on standardized criteria aligned with RTO testing protocols
    \item Provide real-time visual/audio feedback for critical errors (e.g., sudden braking, lane violations)
    \item Export session reports in PDF/CSV format for instructor review
\end{itemize}

\textbf{FR5: Scenario Management and Curriculum Integration}
\begin{itemize}
    \item Offer pre-defined training scenarios: urban roads, highways, parking, emergency braking, obstacle avoidance
    \item Allow instructor-controlled difficulty adjustment (traffic density, time of day, weather)
    \item Support session pause/resume and instant replay for error analysis
    \item Maintain user profiles with progress tracking across multiple sessions
\end{itemize}

\subsection{Non-Functional Requirements}

\textbf{NFR1: Cost Effectiveness}
\begin{itemize}
    \item Target total system cost $<$ \$5000 (headset + custom hardware + PC) to be affordable for driving schools~\cite{Silvera2022}
    \item Use consumer-grade components (Meta Quest 3, off-the-shelf sensors, 3D-printable enclosures)
    \item Minimize recurring costs (no subscription fees for core functionality)
\end{itemize}

\textbf{NFR2: Usability and Accessibility}
\begin{itemize}
    \item Enable setup and calibration within 10 minutes by non-technical driving instructors
    \item Support adjustable seating position and control placements for users 150–200 cm height
    \item Provide intuitive UI with minimal learning curve for first-time VR users
    \item Include safety features: guardian boundary system, emergency stop button, comfort-mode reduced motion
\end{itemize}

\textbf{NFR3: Reliability and Maintainability}
\begin{itemize}
    \item Ensure Bluetooth connection stability with automatic reconnection on signal loss
    \item Design modular hardware allowing component replacement without full system disassembly
    \item Provide diagnostic logs for troubleshooting connection, calibration, and performance issues
    \item Support firmware updates via wireless OTA for bug fixes and feature enhancements
\end{itemize}

\textbf{NFR4: Scalability and Extensibility}
\begin{itemize}
    \item Architecture must support addition of new vehicle models, environments, and training scenarios without core code refactoring
    \item Enable future integration of motion platforms, haptic seats, or force-feedback steering wheels
    \item Allow deployment on both tethered PC-VR and standalone Quest mode with adjustable graphics fidelity
\end{itemize}

\section{Constraints and Design Trade-offs}

\subsection{Hardware Constraints}
\textbf{C1: VR Headset Limitations}
\begin{itemize}
    \item The Meta Quest 3's mobile chipset limits achievable polygon count and texture resolution when rendering natively on-device.
    \item Trade-off: prioritise frame rate stability over maximum visual fidelity to reduce simulator sickness risk.
    \item Solution adopted: the system is deployed as a PC-hosted application streamed to the headset via Meta Quest Link, offloading rendering to desktop GPU hardware rather than the headset's onboard chipset. This resolves the constraint directly rather than requiring aggressive on-device optimisation.
\end{itemize}

\textbf{C2: Racing Wheel Hardware Compatibility}
\begin{itemize}
    \item USB HID racing wheel hardware (Logitech G29) requires host-side driver initialisation that is not supported by the Quest 3's Android-based operating system in a standalone deployment.
    \item Trade-off: a fully standalone deployment would need to forgo physical wheel hardware in favour of hand-tracking-only or Quest controller input, sacrificing control realism.
    \item Solution adopted: the PC-hosted Meta Quest Link architecture (Section~\ref{sec:control_input_architecture}) allows the racing wheel to connect directly to the PC, where standard Windows USB HID drivers apply without limitation.
\end{itemize}

\textbf{C3: Force Feedback}
\begin{itemize}
    \item Force feedback steering resistance, while supported by the G29's hardware, has not yet been integrated into the simulation software.
    \item Trade-off: reduced haptic realism for road-surface and cornering-load feedback versus development time allocated to core simulation stability.
    \item Mitigation: audio feedback (tyre skid sound, engine load) partially compensates; force feedback integration is identified as future work (Chapter~\ref{ch:conclusion}).
\end{itemize}

\subsection{Software and Performance Constraints}
\textbf{C4: Physics Engine Fidelity}
\begin{itemize}
    \item Unity's built-in WheelCollider physics component is optimised for general-purpose vehicle games rather than driver-training-grade accuracy.
    \item Trade-off: computational cost of high-fidelity tyre slip modelling versus frame rate stability.
    \item Solution adopted: WheelCollider suspension and friction curve parameters were iteratively tuned against qualitative real-world handling comparisons rather than implementing a full Pacejka tyre model, balancing accuracy against development time and runtime performance.
\end{itemize}

\textbf{C5: NPC Traffic Behaviour Complexity}
\begin{itemize}
    \item Reliable multi-vehicle NPC navigation at signalised intersections is a recognised open problem in traffic simulation, not unique to this project.
    \item Trade-off: sophisticated traffic-flow algorithms (e.g., reinforcement-learning-based driver agents) versus a deterministic, debuggable rule-based approach appropriate for a training simulator where predictable AI behaviour is preferable to emergent complexity.
    \item Solution adopted: a finite state machine NPC controller (Chapter~\ref{ch:methodology}) with explicit states and yield-priority ordering, favouring predictability and debuggability over behavioural sophistication.
\end{itemize}

\section{Design Alternatives and Justification}

\subsection{VR Platform Selection}
\textbf{Alternatives Considered:}
\begin{enumerate}
    \item \textbf{Valve Index + PC:} Pros: superior field of view (130°) and refresh rate (144 Hz). Cons: high combined cost, wired tethering by design, no native hand tracking.
    \item \textbf{Meta Quest 3:} Pros: wireless standalone capability, affordable relative to PC-VR headsets, inside-out tracking, native hand tracking, and — critically for this project — Meta Quest Link support enabling a PC-hosted fallback architecture. Cons: lower on-device processing power than a dedicated PC-VR headset.
    \item \textbf{PSVR2 + PlayStation 5:} Pros: affordable bundle cost, controller haptics. Cons: closed development ecosystem unsuitable for a research/education project requiring custom Unity development.
\end{enumerate}
\textbf{Selected: Meta Quest 3} — Justification: the Quest 3's support for Meta Quest Link proved decisive, as it enabled the PC-hosted architecture that resolved the racing wheel compatibility constraint (C2) while retaining the headset's native hand tracking, a requirement not met by pursuing a PC-VR-only headset that would need separate hand-tracking hardware.

\subsection{Game Engine Selection}
\textbf{Alternatives Considered:}
\begin{enumerate}
    \item \textbf{Unity:} Pros: mature XR Interaction Toolkit with first-class Meta Quest Link and OpenXR support, extensive C\# scripting ecosystem, large asset store for vehicle and environment assets.
    \item \textbf{Unreal Engine:} Pros: superior default rendering fidelity, built-in Chaos vehicle physics. Cons: steeper learning curve for the development team, less mature Quest hand-tracking integration at project outset.
    \item \textbf{CARLA Simulator:} Pros: purpose-built for driving simulation research. Cons: primarily Python-based with limited native VR headset support, requiring substantial custom integration work.
\end{enumerate}
\textbf{Selected: Unity 6} — Justification: Unity 6's XR Interaction Toolkit provided direct, well-documented support for the Meta Quest Link and hand-tracking pipeline central to this project's architecture, and the team's existing C\# familiarity favoured faster iteration during development.

\label{sec:control_input_architecture}
\subsection{Control Input Architecture}
\textbf{Alternatives Considered:}
\begin{enumerate}
    \item \textbf{Custom ESP32-based Bluetooth controls:} Pros: potentially lower per-unit hardware cost, wireless operation, full design customisability. Cons: requires custom PCB and sensor integration work, introduces calibration and reliability variables, and — most significantly — a Bluetooth Low Energy HID device still requires host-side driver support that the Quest 3 standalone environment does not provide, meaning this approach does not resolve the same underlying platform constraint (C2) as a commercial USB wheel connected via a PC-hosted architecture.
    \item \textbf{Budget commercial racing wheel (Nitho Drive Pro One):} Pros: low cost, plug-and-play PC compatibility. Cons: found through direct testing to have insufficient rotation range (270° vs 900° for real vehicles), an undersized wheel, and pedal spacing too narrow for reliable use while wearing a VR headset (Chapter~\ref{ch:methodology}).
    \item \textbf{Premium commercial racing wheel (Logitech G29):} Pros: 900° rotation range matching real vehicles, full-size wheel, force feedback capability, separated pedal set resolving the identification problem observed with the budget unit, and native USB HID compatibility with a PC-hosted architecture. Cons: higher unit cost than a custom or budget solution.
\end{enumerate}
\textbf{Selected: Logitech G29 via PC-hosted USB connection} — Justification: direct user testing (Chapter~\ref{ch:results}) confirmed the G29 was rated substantially more realistic than the budget alternative, and its native USB HID compatibility with a Windows PC directly resolved the standalone-deployment driver incompatibility that motivated reconsideration of the originally proposed ESP32-based approach. This decision was made after the ESP32 approach was determined, during early development, to face the same platform-level input constraint as any USB or BLE HID device attempting standalone Quest 3 operation.

\section{System Objectives}
Based on the requirements analysis and design trade-offs, the system objectives are:
\begin{itemize}
    \item To design a VR-based driving simulation environment replicating realistic vehicle control and handling behaviour.
    \item To integrate a commercially available racing wheel and pedal set providing physically realistic steering, throttle, and braking input.
    \item To ensure compatibility with the Meta Quest 3 headset via a PC-hosted Meta Quest Link architecture, retaining full head-tracking and hand-tracking functionality.
    \item To provide a structured, progressive-difficulty set of training environments suitable for novice driver familiarisation through to advanced intersection navigation.
    \item To develop a system using consumer-accessible hardware components, avoiding the cost and complexity of dedicated commercial simulator infrastructure.
\end{itemize}

\section{System Components and Architecture}

The system architecture consists of three tightly integrated subsystems.

\subsection{Hardware Interface Subsystem}
\begin{itemize}
    \item \textbf{Racing Wheel:} Logitech G29 Driving Force, offering 900° steering rotation, force feedback capability, and separated accelerator/brake/clutch pedals connected via USB to the host PC.
    \item \textbf{Gear Shifter:} Logitech Driving Force Shifter, an H-pattern mechanical shifter connecting to the G29 base, providing physical gear selection input.
    \item \textbf{VR Headset:} Meta Quest 3, providing head tracking, optical hand tracking, and stereoscopic display, connected to the host PC via Meta Quest Link (wired USB-C or wireless Air Link).
\end{itemize}

Both the racing wheel/shifter assembly and the VR headset connect to the same host PC, which runs the Unity application and coordinates all input and rendering.

\subsection{Software Simulation Subsystem}
Developed in Unity 6 with the following modules:
\begin{itemize}
    \item \textbf{Input Manager:} Reads racing wheel and pedal axis data via Unity's Input System, applying deadzone filtering and the pedal-axis remapping required by the G29's inverted resting-position convention (Chapter~\ref{ch:methodology}).
    \item \textbf{Vehicle Physics Engine:} Built on Unity WheelCollider components with custom-tuned suspension, friction, and drivetrain logic implementing front-wheel-drive behaviour and a four-position automatic gearbox.
    \item \textbf{Environment System:} Three hand-crafted training environments hosted within a single scene, with a state-machine-driven NPC traffic controller providing signalised intersection navigation in the city environment.
    \item \textbf{VR Interaction:} XR Interaction Toolkit providing head tracking, hand-tracking-based cockpit interaction (steering wheel, horn), and a world-space VR menu for environment selection.
\end{itemize}

\subsection{VR Interface Subsystem}
The Meta Quest 3 headset provides:
\begin{itemize}
    \item \textbf{Head Tracking:} Six-degrees-of-freedom inside-out tracking via onboard cameras, passed through to the host PC via Meta Quest Link.
    \item \textbf{Hand Tracking:} Optical hand tracking used for in-cockpit interactions, similarly passed through via Meta Quest Link's OpenXR implementation.
    \item \textbf{Stereoscopic Rendering:} Rendered content is computed on the host PC GPU and streamed to the headset display via Meta Quest Link, rather than rendered natively on-device.
\end{itemize}

Deployment mode: PC-hosted via Meta Quest Link, connecting either by USB-C cable or wirelessly via Air Link.

\section{Design Rationale Summary}

\begin{itemize}
    \item \textbf{Consumer-hardware accessibility:} using a commercial racing wheel and consumer VR headset avoids the cost, fabrication risk, and calibration overhead of custom electronics while still meeting the project's physical-realism requirements.
    \item \textbf{Platform compatibility resolution:} the PC-hosted Meta Quest Link architecture directly resolves the fundamental incompatibility between USB/BLE HID racing wheel hardware and standalone Quest 3 operation.
    \item \textbf{Retained VR capability:} despite not being a fully standalone deployment, the system retains full head-tracking and hand-tracking functionality identical to native operation.
    \item \textbf{Predictable NPC behaviour:} a deterministic finite-state-machine traffic controller was prioritised over more complex adaptive AI approaches, favouring debuggability and behavioural predictability appropriate for a training context.
\end{itemize}

\subsection{Detailed Functional Flow}
\begin{enumerate}
    \item \textbf{Pre-Session Setup (2–5 minutes):}
    \begin{itemize}
        \item Instructor selects trainee profile, training scenario (e.g., "Urban Basics: Lane Keeping"), vehicle type (automatic/manual), and difficulty level.
        \item Trainee dons Quest 3 headset; system initiates guardian boundary setup and comfort calibration (IPD adjustment, brightness).
        \item Hardware connection handshake: Steering wheel, pedals, and shifter auto-pair via Bluetooth; system runs diagnostic check (sensor ranges, battery level).
        \item Virtual environment loads: vehicle spawns at scenario starting position; HUD displays initial instructions ("Adjust seat, check mirrors, fasten seatbelt").
    \end{itemize}
    
    \item \textbf{Simulation Loop (15–30 minutes typical session):}
    \begin{itemize}
        \item \textbf{Input Capture (20 Hz):} ESP32 samples sensors (steering angle, pedal positions, gear state) → transmits via BLE HID packets.
        \item \textbf{Physics Update (60 Hz):} Unity's FixedUpdate applies forces to vehicle rigidbody based on input → calculates acceleration, tire slip, suspension compression.
        \item \textbf{Collision \& Traffic AI (30 Hz):} Raycast-based collision detection; traffic agents follow waypoint paths with lane-change logic; pedestrians obey traffic signals.
        \item \textbf{Rendering (90 Hz):} Stereoscopic camera renders scene from driver's viewpoint → foveated rendering reduces peripheral detail → Quest 3 displays frames.
        \item \textbf{Audio Spatialization (60 Hz):} FMOD calculates 3D engine sound (RPM-dependent), tire squeal (slip-dependent), horn/indicator clicks → Quest 3 speakers.
        \item \textbf{Real-time Assessment:} Background thread logs events (speed violations, lane crossings, harsh braking) → updates live feedback HUD (color-coded indicators).
    \end{itemize}
    
    \item \textbf{Event Handling:}
    \begin{itemize}
        \item \textbf{Scenario Triggers:} Dynamic events (e.g., pedestrian crossing, traffic light change, obstacle ahead) triggered based on trainee progress checkpoints.
        \item \textbf{Instructor Override:} Wireless tablet interface allows real-time weather change, traffic density adjustment, or scenario pause for coaching feedback.
        \item \textbf{Comfort Monitoring:} Optional: Detect prolonged stationary gaze (potential nausea indicator) → suggest break.
    \end{itemize}
    
    \item \textbf{Session Termination:}
    \begin{itemize}
        \item Trainee completes scenario objectives (e.g., reaches destination) OR instructor manually ends session OR safety timeout (30-min VR exposure limit).
        \item System saves session data: timestamped input logs, trajectory GPS coordinates, metric summaries.
    \end{itemize}
    
    \item \textbf{Post-Session Assessment (2 minutes):}
    \begin{itemize}
        \item Assessment module computes scores: (1) Speed Compliance (85/100), (2) Lane Discipline (78/100), (3) Smooth Braking (92/100), (4) Gear Shifting (Manual only, 88/100), (5) Observation (mirror checks, 70/100).
        \item Generates PDF report with score breakdown, heatmap of violations on route map, improvement suggestions.
        \item Updates trainee profile: increments training hours, marks scenario as "Passed" (if overall $>$ 75\%) or "Retry Recommended."
        \item Instructor reviews report with trainee; schedules follow-up session or progresses to advanced scenarios.
    \end{itemize}
\end{enumerate}

\section{Feasibility Study}

A comprehensive feasibility analysis is essential to validate the viability of the VR Driving Simulator project across technical, economic, operational, and schedule dimensions. This section systematically evaluates each feasibility aspect to establish project confidence and identify potential risk mitigation strategies.

\subsection{Technical Feasibility}

\textbf{Hardware Capabilities and Limitations:}
The project relies on consumer-grade VR hardware (Meta Quest 3) and custom Bluetooth control assemblies. Technical feasibility is high given the following established capabilities:

\begin{itemize}
    \item \textbf{VR Headset Performance:} Meta Quest 3 offers 90--120 Hz refresh rates, 2064×2208 pixels per eye, and inside-out tracking with sub-millimeter accuracy. These specifications meet the minimum requirements for comfortable, immersive driving simulation~\cite{Lindal2019,Weidner2017}. The standalone architecture eliminates PC tethering constraints, enhancing portability for driving school deployments.
    
    \item \textbf{Bluetooth Control Latency:} ESP32 microcontroller with BLE 5.0 achieves input-to-response latency of 30--50ms in controlled tests. While this marginally exceeds the 20ms ideal threshold for high-fidelity force feedback systems~\cite{Harari2021}, it remains within acceptable bounds for educational driving training where reaction time is less critical than in competitive racing scenarios. Mitigation strategies include predictive input smoothing and local sensor fusion on the ESP32 to reduce jitter.
    
    \item \textbf{Physics Simulation Complexity:} Unity's built-in physics engine (PhysX) supports realistic vehicle dynamics at 60 Hz fixed timestep. Custom wheel collider scripts can model differential torque, suspension travel, and tire slip based on Pacejka tire models. Benchmark tests on similar projects~\cite{Silvera2022} demonstrate that mid-range desktop GPUs (RTX 3060 equivalent) can maintain 90 FPS stereoscopic rendering with 20--30 dynamic traffic agents, meeting real-time performance targets.
    
    \item \textbf{Integration Challenges:} Cross-platform compatibility between Quest 3 (Android-based) and Unity (Windows development environment) requires careful build configuration. Oculus Integration SDK and XR Plugin Management provide mature toolchains with extensive documentation. Initial prototyping confirms successful BLE pairing and input mapping via Unity Input System without major technical blockers.
\end{itemize}

\textbf{Risk Assessment:} Technical risks are low to moderate. The primary concern is sustained 90 FPS performance under complex scenarios (heavy rain, dense urban traffic). Mitigation involves progressive scene optimization (occlusion culling, LOD models, asynchronous asset loading) and adaptive quality settings based on real-time frame rate monitoring.

\subsection{Economic Feasibility}

\textbf{Cost-Benefit Analysis:}
Economic viability is evaluated by comparing the actual development cost incurred against the cost of commercial alternatives, based on hardware acquired during this project rather than a hypothetical projected cost.

\textbf{Development Costs Incurred:}
\begin{itemize}
    \item \textbf{Racing Wheel and Shifter:} Logitech G29 Driving Force and Logitech Driving Force Shifter, acquired via project funding request (Appendix~\ref{app:funding}).
    \item \textbf{VR Headset:} Meta Quest 3, used as the primary development and testing headset.
    \item \textbf{Software:} Unity 6 Personal edition (no licensing cost at current development scale); no paid third-party asset packages were required beyond the vehicle and environment models used.
    \item \textbf{Development Labour:} Single-student development effort over the current project timeline, supervised by the project guide.
\end{itemize}

\textbf{Comparative Economics:}
Commercial dedicated driving simulators — including motion-platform and multi-screen installations used in some professional driving instruction contexts — typically cost several times more than the consumer hardware combination used in this project (a Meta Quest 3 headset and a mid-range commercial racing wheel). Precise return-on-investment or break-even projections for driving-school deployment are not presented here, as this project has not yet reached a pilot deployment stage; such analysis is identified as future work contingent on the formal user study and any subsequent institutional partnership (Chapter~\ref{ch:conclusion}).

\textbf{Economic Verdict:} The hardware cost of the current system compares favourably against commercial simulator alternatives on a qualitative basis. A rigorous cost-benefit and ROI analysis requires deployment-scale data not yet available at this stage of the project and is deferred to future work.

\subsection{Operational Feasibility}

\textbf{User Acceptance and Usability:}
Operational feasibility has been assessed qualitatively through informal testing sessions with the supervising faculty member and additional volunteer participants, as detailed in Chapter~\ref{ch:results}. No formal instructor onboarding protocol, curriculum integration study, or structured usability survey has yet been conducted; these are identified as necessary steps prior to any driving-school deployment.

\begin{itemize}
    \item \textbf{Learner Comfort:} Preliminary observations (Chapter~\ref{ch:results}) indicate that simulator sickness is present in VR-inexperienced users initially, with symptoms reducing across repeated sessions. This is consistent with patterns reported in prior literature on VR acclimatisation, but has not yet been quantified for this specific system using a standardised instrument such as the Simulator Sickness Questionnaire.
    \item \textbf{Hardware Setup:} The system requires a PC capable of running Unity applications, a Meta Quest 3 headset, and the racing wheel/shifter assembly connected via USB — a moderate but not extensive infrastructure requirement compared to dedicated simulator installations.
    \item \textbf{Maintenance:} No formal durability or long-duration reliability testing has been conducted at this stage. Hardware maintenance considerations are limited to standard care of consumer VR and racing wheel peripherals.
\end{itemize}

\textbf{Organisational Readiness:}
No formal engagement with driving schools or regulatory bodies has taken place at this stage of the project. Any future deployment consideration would require the structured evaluation and institutional partnership discussed in Chapter~\ref{ch:conclusion}.

\textbf{Operational Verdict:} Provisionally feasible based on informal testing, but formal operational feasibility — instructor training requirements, curriculum integration, and institutional adoption — remains to be established through the structured evaluation planned as future work.

\textbf{Intellectual Property and Licensing:}
\begin{itemize}
    \item \textbf{Software Licensing:} Unity Pro educational license permits non-commercial academic projects. Open-source release under MIT License planned to encourage community adoption~\cite{Silvera2022}.
    \item \textbf{Asset Usage:} Vehicle 3D models sourced from Unity Asset Store with appropriate licenses (Standard License allows unlimited project use; Extended License not required for educational distribution). Custom textures created in-house avoid copyright concerns.
    \item \textbf{Patent Landscape:} Prior art search reveals no blocking patents for Bluetooth driving controls in VR training. Generic input mapping techniques fall under established prior art. Novel contributions (e.g., clutch engagement modeling algorithm) potentially patentable but not pursued during academic phase.
\end{itemize}

\textbf{Safety and Liability:}
\begin{itemize}
    \item \textbf{VR Safety Guidelines:} System complies with Oculus Health \& Safety warnings: age restriction (13+), seizure/motion sickness disclaimers, play area boundary setup. Informed consent forms distributed to pilot testers.
    \item \textbf{Training Validity:} Current Indian regulations do not recognize VR training hours toward RTO learning license requirements. System positioned as supplemental training tool, not replacement for mandatory on-road practice. Future advocacy for regulatory acceptance requires longitudinal validation studies (beyond project scope)~\cite{He2022}.
\end{itemize}

\textbf{Data Privacy:}
Session logs (driving metrics, error patterns) constitute personal performance data. System complies with data minimization principles: no video recording of users, no biometric data collection, anonymized identifiers for analytics. GDPR-equivalent consent mechanisms (opt-in data sharing for research) implemented.

\textbf{Legal Verdict:} Feasible with standard precautions. No legal blockers identified for academic prototype development and pilot testing. Commercial deployment requires legal entity formation, liability insurance, and formal safety certifications (ISO 26262 compliance for automotive training systems).
